# Интеграционные тесты (Playwright)

Проверяют frontend и backend вместе, через реальный браузер (Chromium): гость бронирует слот,
владелец смотрит встречи и управляет типами событий.

## Предпосылки

- Node 22.18+ (как для `backend/`).
- Установлены зависимости `backend/` и `frontend/` (`npm install` в каждой директории) — их
  `npm run dev` поднимает Playwright через `webServer`, отдельно запускать не нужно.

## Установка

```bash
cd e2e
npm install
npx playwright install --with-deps chromium
```

## Запуск

```bash
npm test           # headless-прогон всех тестов
npm run test:ui    # интерактивный UI-режим Playwright для отладки
npm run test:report # открыть HTML-отчёт последнего прогона
```

При старте `playwright.config.ts` сам поднимает `backend` (`npm run dev`, :3000) и `frontend`
(`npm run dev`, :5173) — если они уже запущены локально, существующие процессы переиспользуются
(`reuseExistingServer`, кроме CI).

## Изоляция тестов без сброса backend

В backend нет эндпоинта сброса in-memory store (см. [AGENTS.md](../AGENTS.md) — API меняется
только через `specs/*.tsp`, заводить тестовый эндпоинт ради этого не стали). Поэтому тесты не
полагаются на чистое состояние, а сами создают уникальные данные:

- **Бронирования** — каждый тест выбирает свой "n-й доступный день" (0-based индекс среди кнопок
  `[aria-label="Выбор дня"]`, у которых нет класса `opacity-60`, см. `tests/helpers/slots.ts`).
  Выходные дни без слотов автоматически пропускаются, поэтому тесты не зависят от даты запуска.
  Диапазоны n закреплены за файлами и не пересекаются:
  - `booking.spec.ts` — n = 0, 1
  - `admin-bookings.spec.ts` — n = 3–8
  - `admin-event-types.spec.ts` — дни не использует
- **Типы событий** — каждый тест создаёт свой тип с уникальным названием (`uniqueTitle()` —
  временная метка + случайный суффикс) и не трогает seed-типы ("Знакомство", "Консультация",
  "Ревью проекта").

Добавляя новый тест, выбирайте n вне занятых диапазонов (или создавайте данные без привязки к
дню — как типы событий) — иначе тест может столкнуться с чужой бронью при повторных прогонах на
живом backend.

Тесты идут строго в один worker (`workers: 1` в `playwright.config.ts`) — backend хранит
состояние в памяти процесса, параллельный запуск ломает детерминизм.

## Структура

```
tests/
  booking.spec.ts             # раздел "Запись": бронирование слота гостем
  admin-bookings.spec.ts      # раздел "Встречи": список и фильтр броней в админке
  admin-event-types.spec.ts   # раздел "Типы событий": CRUD типов событий в админке
  helpers/slots.ts            # выбор дня/слота, создание брони через UI, уникальные названия
```

Полный список тест-кейсов с шагами и ожидаемым результатом — в [../README.md](../README.md#интеграционные-тесты)
и в описаниях самих тестов (`test(...)` с префиксом `TC-*`).

## CI

Workflow [`.github/workflows/e2e.yml`](../.github/workflows/e2e.yml) устанавливает зависимости
backend/frontend/e2e, ставит Chromium и гоняет `npm test`. При падении тестов в артефакты
прогона (`playwright-report`) попадает HTML-отчёт со скриншотами и трейсами — доступен на
вкладке Actions → соответствующий workflow run → Artifacts.
